# R5.3b Dispatched sessions as Claude Code background agents

Last reviewed: 2026-11-05 (through D0022)

**Asked:** the person wants every worker and verifier foreman starts to show up in Claude Code's own agent view (`claude agents`, `claude attach`, `claude logs`, `claude stop`), instead of running as `claude -p` processes under a separate `CLAUDE_CONFIG_DIR` that only foreman knows about. Isolation ([D0011](../decisions/D0011-foreman-dispatch.md), [D0003](../decisions/D0003-one-agent-config.md)) must not get weaker. Task T-0068.

**Result: switch, with five things foreman has to do itself.** A `claude --bg` session that runs on the person's own config dir, with the flags below, saw exactly what today's launch is meant to let through: the repo's CLAUDE.md, the project's hooks and skills, and the MCP server foreman passed. It did not see the user's CLAUDE.md, rules, hooks, skills, agents, commands or MCP servers, the CLAUDE.md files above the repo, or the claude.ai connectors. It is also tighter than today: today's print-mode launch still gives a session every claude.ai connector and the account's synced skills (below).

The five things:
1. **Pass foreman's environment through `--settings` `env`.** A `--bg` session doesn't inherit the environment of the process that ran `claude --bg`. Without this, `FOREMAN_ACTOR` is missing and the guard treats the session as the person's (no task paths, no role rules).
2. **Turn auto memory off** (`autoMemoryEnabled: false`), or the person's memory for that project loads.
3. **Enforce the limits.** `--max-turns` and `--max-budget-usd` are accepted but ignored. Foreman watches the transcript and stops the session.
4. **Set `--permission-mode dontAsk`.** Otherwise a session that hits a permission prompt waits for a person, and holds its lease while it waits.
5. **Stop sessions when they're done.** A `--bg` session doesn't exit when its turn ends. It sits idle until someone stops it.

Intake stays in print mode: it needs `--json-schema`, which works only with `--print`, and `--bg` refuses `--print`.

## How it was run

On Claude Code 2.1.318, with `claude-haiku-5-5`, in a scratch repo (`/tmp/zqx-bg/anc/work/demo`, no real project). It took 13 `--bg` sessions and 2 print-mode runs, about $0.12; `--bg` reports no cost, so that figure is estimated from the token counts at Haiku 5.5 prices.

**The person's config dir had a stand-in.** `--bg` refuses an untrusted workspace ("Workspace not trusted. Run `claude` in … once and accept the trust prompt"). Accepting that prompt in the person's real `~/.claude` for a scratch dir is the person's call, not a worker's. So the runs used `CLAUDE_CONFIG_DIR=/tmp/zqx-bg/person`, a config dir laid out like `~/.claude` with a marker in every user-level place Claude Code reads:
- `CLAUDE.md`, `rules/u.md` and `projects/<repo>/memory/MEMORY.md` (auto memory);
- `skills/zqx-user-skill/`, `agents/zqx-user-agent.md` and `commands/zqx-user-cmd.md`;
- `settings.json` with SessionStart, UserPromptSubmit and PreToolUse hooks, each touching a file;
- `.claude.json` with a user MCP server and a local-scope MCP server, each a canary stdio server that touches a file when it starts;
- the trust entry for the repo, and `.credentials.json` linked to the real login, so the claude.ai connectors come from the real account.

Claude Code finds every one of these relative to the config dir, so the real `~/.claude` behaves the same way.

Outside the stand-in dir:
- **Above the repo:** `/tmp/zqx-bg/anc/CLAUDE.md` and `/tmp/zqx-bg/anc/.claude/rules/r.md`, as in D0011's ancestor case.
- **In the repo:** a `CLAUDE.md` marker, a project skill, and a project PreToolUse hook on Read that writes `$FOREMAN_ACTOR` to a file.

What each session saw came from two places:
- its answer to a fixed prompt (read README.md, then list every `ZQX-…` token, instruction file, `mcp__` tool, skill and agent type);
- the transcript's own attachments (`instructions`, `skill_listing`, `agent_listing_delta`, `deferred_tools_delta`), which say what Claude Code loaded without relying on the model.

The marker files showed which hooks and MCP servers ran.

The isolated launch:

```sh
cd /tmp/zqx-bg/anc/work/demo
CLAUDE_CONFIG_DIR=/tmp/zqx-bg/person claude --bg --name zqx-iso2 --model claude-haiku-5-5 \
  --setting-sources project,local \
  --strict-mcp-config --mcp-config '{"mcpServers":{"zqxforeman":{"type":"stdio","command":"bun","args":["mcp-canary.ts","zqx_foreman_tool","…/foreman-mcp-ran"]}}}' \
  --settings '{"claudeMdExcludes":["/tmp/zqx-bg/anc/CLAUDE.md","/tmp/zqx-bg/anc/.claude/rules/**"],"autoMemoryEnabled":false,"env":{"FOREMAN_ACTOR":"worker-T-ZQX"}}' \
  --allowedTools Read,mcp__zqxforeman__zqx_foreman_tool --permission-mode dontAsk \
  -- "$(cat p-iso.txt)"
```

The control run was the same command without `--setting-sources`, `--strict-mcp-config`, `--mcp-config` and `--settings`.

## 1. Does `--bg` on the person's config dir isolate as well as the separate config dir?

Yes, once auto memory is off. Each row is one source; ✗ means it didn't reach the session.

| Source | Control `--bg` | Isolated `--bg`, first try | Isolated `--bg` + `autoMemoryEnabled:false` | Today: `-p`, own config dir |
|---|---|---|---|---|
| User `CLAUDE.md` | seen | ✗ | ✗ | ✗ (own dir) |
| User `rules/` | seen | ✗ | ✗ | ✗ |
| CLAUDE.md and rules above the repo | seen | ✗ (claudeMdExcludes) | ✗ | ✗ |
| Auto memory (`projects/<repo>/memory/MEMORY.md`) | seen | **seen** | ✗ | ✗ (own dir) |
| User skills, agents, commands | seen | ✗ | ✗ | ✗ |
| Account-synced skills (`anthropic-skills:*`) | seen | ✗ | ✗ | **seen** |
| User hooks (SessionStart, UserPromptSubmit, PreToolUse) | ran | ✗ | ✗ | ✗ |
| User and local-scope MCP servers | started | ✗ | ✗ | ✗ |
| claude.ai connectors (Gmail, Slack, Notion, Drive, …) | seen | ✗ (`--strict-mcp-config`) | ✗ | **seen** |
| Project CLAUDE.md, project skill | seen | seen | seen | seen |
| Project PreToolUse hook | ran | ran | ran | ran |
| The MCP server foreman passes | n/a | started | started | n/a |

Today's dispatcher passes no `--mcp-config`, so `--strict-mcp-config` isn't set, and the claude.ai connectors and account skills reach every worker. A worker can't call them: in print mode, tools outside `--allowedTools` are denied. But their descriptions sit in the session's context, and the `Skill` tool is allowed. `--strict-mcp-config` is what removes the connectors, in either mode.

The other flags behave as in print mode:
- **`--disallowedTools`:** a session with `--allowedTools Read,Bash --disallowedTools 'Bash(printenv *)'` was refused the `printenv` call.
- **The project's hooks run, and see what `--settings` sets:** the project hook wrote `actor=worker-T-ZQX`, the value given only in `--settings` `env`.

**The environment is not inherited.** A session started with `FOREMAN_ACTOR=worker-T-ZQX FOREMAN_AGENT=1 ZQX_PROBE=env-ok claude --bg …` ran `printenv FOREMAN_ACTOR FOREMAN_AGENT ZQX_PROBE HOME` and got only `/root`. The session runs under Claude Code's background service, and its job record keeps just `CLAUDE_CONFIG_DIR` (`providerEnv`). With the same values in `--settings '{"env":{…}}'`, the printenv call returned all three, and so did the hook.

What's left over, all of it in the person's own files, none of it reaching a session:
- **Prompt history:** foreman's prompts are added to the person's `history.jsonl`, the up-arrow history.
- **`~/.claude.json`** gains one project entry per worktree (Claude Code's normal per-directory state). `claude purge <path>` removes one.
- **Transcripts and job records** go to `~/.claude/projects/` and `~/.claude/jobs/`. This is the point of the switch.
- **Same as today:** the account (its email reaches the session as `session_context`) and managed policy settings.
- **Not tested:** plugins. The stand-in dir had none installed. They're switched on by `enabledPlugins` in user settings, which `--setting-sources project,local` doesn't load, so they shouldn't reach a session. The T-0069 live test should check.

**Trust.** `--bg` checks workspace trust, which `-p` skips. Trust carried over from the trusted repo to a subdirectory and to a git worktree inside the repo (where foreman puts them). It didn't carry over from a trusted directory above the git root (`/tmp/zqx-bg`). So foreman's worktrees are trusted once the person has trusted the main checkout, which they have for any repo they've opened in Claude Code.

## 2. How a prompt, model, max turns and budget are passed

- **Prompt:** the positional argument, after `--`. `claude --bg -p` is refused: "`--bg` and `--print` conflict: `--print` never starts the interactive session that `claude agents` attaches to".
- **Model:** `--model`.
- **Max turns and budget: ignored.** A session with `--max-turns 2 --max-budget-usd 0.001` did all five reads it was asked for, in 7 API calls and well over $0.001. The job record kept both flags in `respawnFlags`; they only work with `--print`. Foreman has to enforce both, and the wall-clock timeout (below).
- **Session name:** `--name` names the session in `claude agents` and the job record (`"nameSource": "user"`), and `claude attach <part of the name>` accepts it.
- **Permission mode:** without `--permission-mode`, the session started in `auto`, the account's default.

## 3. What `claude agents --json [--all]` gives, and where the rest is

`claude agents --json` lists the running sessions; `--all` adds the stopped ones. Each entry has: `pid`, `id` (short), `cwd`, `kind` (`background` or `interactive`), `startedAt`, `sessionId`, `name`, `status` and `state`.

| Field | Values seen |
|---|---|
| `status`: the process | `busy`, `idle` (turn over), `waiting` (at a permission prompt), `null` (stopped, with `pid: null`) |
| `state`: the model's own label | `working`, `done`, `blocked` |

There is no cost, turn count or exit code. The session doesn't exit, so there's no exit code to have.

What else there is:
- **Job record, `<config>/jobs/<id>/state.json`:** `state`, a one-line `detail` the session writes, and `output.result`, a summary, not the reply. It also has `sessionId`, `cwd`, `respawnFlags`, `intent` (the prompt), `providerEnv`, timestamps, and `linkScanPath`, the transcript path.
- **`state` can lag.** The control session stayed `working` in `state.json` and in the list after its turn had ended (`status: idle`). Use `status` for "is it still going". `state` is the session's own word for done or stuck.
- **Timeline, `<config>/jobs/<id>/timeline.jsonl`:** one line per state change. A line's `text` is the reply in full when the turn ends, e.g. `{"state":"done","detail":"…","text":"DONE-READING"}`.
- **Transcript, `<config>/projects/<cwd with / as ->/<sessionId>.jsonl`:** assistant messages with `usage` (input, output, cache read, cache write). So:
  - turns = the number of assistant messages;
  - cost = usage × a price table, because there's no `total_cost_usd`;
  - the transcript's `instructions` attachment lists every memory file the session loaded.
- **`claude logs <id>`:** the terminal screen, ANSI and all. Good for a person, not something to parse.

## 4. What happens at a permission prompt

With `--permission-mode default` and only `Read` allowed, asking for `echo hi > perm-test.txt` left the session at the prompt ("Do you want to proceed? 1. Yes 2. Yes, and always allow … 4. No"). Its `status` was `waiting` and its `state` `blocked`. It stayed there until it was stopped, about eight minutes later. Nothing was written. A person could `claude attach` and answer.

With `--permission-mode dontAsk`, the same call was refused at once, the session went on, and it ended `idle` / `blocked` with "denied by permission mode". That's what print mode does today. Use `dontAsk`, and have foreman flag a session it sees `waiting`.

## 5. Does the session appear in the person's `claude agents` and `claude --resume`?

Yes, in the views of whichever config dir it ran under. The probes appeared in `CLAUDE_CONFIG_DIR=/tmp/zqx-bg/person claude agents`; this worker's own parent, started with `--bg` on the person's dir, appears in the person's `claude agents`. With no `CLAUDE_CONFIG_DIR` override, dispatched sessions land in the person's list.

After `claude stop fc3b6139`:
- the session stayed in `--all` with `status: null`;
- `claude --resume fc3b6139-ab6e-… -p "What word did you reply with at the end of your last turn?"` answered `DONE-READING`.

Transcripts are kept under the worktree's path, so `/resume` run from inside the worktree lists them. `claude attach <id>` reopens a stopped session too.

## 6. Do `--bg` sessions survive the dispatcher exiting?

Yes, by design. `claude --bg` returns in about a second ("backgrounded · 6f40786f · zqx-probe-basic"). The session's parent is the background service's pty host (`claude bg-pty-host --bg-pty-host /tmp/cc-daemon-0/<hash>/…`), in its own process group and session, so foreman exiting or being killed doesn't touch it. Consequences:
- **Stopping:** foreman's kill-on-exit and process-group kill no longer reach the session. Stopping means `claude stop <id>`.
- **The lease:** it can still be pinned to the PID from `claude agents --json`. A finished session stays alive at the prompt, though, so foreman must stop it, or the lease never ends.
- **Picking up after a restart:** a foreman that restarts can find its sessions again, by the name `worker-T-0042` and the job record's `cwd`.

## Cleanup

Every probe was stopped and removed (`claude stop`, `claude rm`), and the stand-in dirs' background services were stopped. No session ran on the person's real config dir.
