# R5.3c Can dispatched workers use subagents?

Last reviewed: 2026-11-12 (through D0047)

**Asked:** dispatched workers ([D0022](../decisions/D0022-background-sessions.md)) are told not to spawn subagents, because "they are cut off when you finish, and their work is lost". So a dispatched worker gets no reviewer, test-writer or docs-writer even on a risky change, where [D0029](../decisions/D0029-faster-sessions.md) says a second pass still pays. Is the reason true, and what would lifting the ban take and cost? Task T-0124.

**Result: the stated reason is no longer true, but one thing must be fixed before the ban can be lifted.** On Claude Code 2.1.322:
- A subagent in a `--bg` session always runs in the background. The parent stays `busy` in `claude agents --json` until the subagent has reported, so foreman's watch loop waits for it. Nothing is cut off.
- Subagents get the worker's environment, guard, path limits and denied tools.
- **Their usage is not in the parent's transcript.** Foreman's turn and cost limits missed 19–47% of the cost and up to 56% of the turns in the runs below.
- A reviewer alone cost 1.5× the dollars of the same task done solo and found a bug the solo run's own review missed. The full three-agent fan-out cost 3.1×.

The decision is [D0047](../decisions/D0047-dispatched-workers-reviewer.md).

## How it was run

Nine `claude --bg` sessions, started from the T-0124 worktree on the person's own config dir, which is where the dispatcher starts them. Each command came from foreman's own `buildLaunch` (role `worker`, task `T-0124`), so the flags are the dispatcher's:

```sh
claude --bg --name zqx-probe-fg \
  --setting-sources project,local \
  --strict-mcp-config --mcp-config '{"mcpServers":{}}' \
  --settings '{"claudeMdExcludes":[…],"autoMemoryEnabled":false,"env":{"FOREMAN_AGENT":"1","FOREMAN_ACTOR":"worker-T-0124","FOREMAN_BIN":"bun <main checkout>/packages/foreman/src/cli.ts"}}' \
  --permission-mode dontAsk \
  --allowedTools Read,Glob,Grep,Edit,MultiEdit,Write,NotebookEdit,Bash,Agent,Skill,TodoWrite,mcp__foreman__… \
  --disallowedTools 'mcp__foreman__start_verify,…,Bash(uname *)' \
  --model claude-haiku-5-5 -- "<prompt>"
```

Two things differ from a real worker:
- **No MCP servers** (`{"mcpServers":{}}`), so a probe running as `worker-T-0124` couldn't submit or edit the real task. The guard doesn't use MCP: it calls foreman's CLI through `FOREMAN_BIN`.
- **`Bash(uname *)` added to `--disallowedTools`** in the first probe, to stand in for a role deny rule ([D0019](../decisions/D0019-role-deny-rules.md)). This repo's `foreman.json` has none.

Because the actor was `worker-T-0124`, the guard held every probe to this task's real paths: `docs/research/R5.3c-*.md` and `docs/decisions/**`.

Sessions P4, P6 and Q5a–c were started and watched by foreman's own `launchBg`, the function the dispatcher uses: it polls `claude agents --json --all` every 2 seconds, stops the session after two idle looks in a row, and sums the transcript. The others were started with the same command and watched by a 3-second poll of `claude agents --json --all`.

What each session did came from its transcript (`~/.claude/projects/<worktree>/<session>.jsonl`), its subagents' transcripts, and its job record (`~/.claude/jobs/<id>/state.json` and `timeline.jsonl`). Costs are foreman's own estimate (`summarizeTranscript`, price table × tokens). The mechanics probes ran on `claude-haiku-5-5` and the cost runs on `claude-sonnet-5-5`; all of it came to about $1.20.

| Run | Prompt, in short | Watched by |
|---|---|---|
| P1 | spawn `reviewer` and `general-purpose` "in the foreground"; each prints its environment, tries allowed and refused writes and a denied command | poll |
| P2, P3 | first tries of P4 and P5; the subagent's command was refused (below), so they showed nothing about timing | `launchBg`, poll |
| P4 | spawn one subagent that runs for 75 seconds and writes a marker file; end the turn at once | `launchBg` |
| P5 | the same, with `run_in_background: false` asked for; `claude stop` while the subagent ran | poll |
| P6 | start a 40-second shell command with `run_in_background`; end the turn at once | `launchBg` |
| Q5a | build a small library, solo | `launchBg` |
| Q5b | the same, with test-writer, docs-writer and reviewer | `launchBg` |
| Q5c | the same, solo plus one reviewer | `launchBg` |

## 1. Do foreground subagents run to completion? Do the project's agents load?

**There are no foreground subagents in a `--bg` session.** Every Agent call returned at once with "Async agent launched successfully … You will be notified automatically when it completes", including the one in P5 that set `run_in_background: false`. Each subagent's `meta.json` says `"requestShape":"background","requestNonInteractive":true`.

What happens instead:
1. The parent's turn ends while the subagents run.
2. Each subagent that finishes wakes the parent with a `<task-notification>` carrying its report. In P1 the parent took three turns: one to spawn, one per report.
3. The parent replies again after the last one.

**They run to completion.** In P4 the subagent ran its full 75 seconds after the parent's turn had ended, wrote its marker file, and the parent then reported it. In Q5b three subagents ran in parallel and all reported.

**The project's agents load.** The parent's `agent_listing_delta` attachment listed `design-critic`, `docs-writer`, `reviewer` and `test-writer` from `.claude/agents/`, beside the built-in types. P1 ran `reviewer`; Q5b ran `test-writer`, `docs-writer` and `reviewer`. No user-level agent was listed.

**Subagents load the same project context:** the subagent's `instructions` attachment held the worktree's `CLAUDE.md` and `AGENTS.md` and nothing from above the repo, and its `skill_listing` held the project's skills.

**One refusal to know about.** In P2 and P3 the subagent's Bash command redirected output to a file under `~/.claude/`, and `dontAsk` refused it: "Permission to use Bash has been denied because Claude Code is running in don't ask mode". The same command writing inside the worktree ran (P4, P5). This is the permission mode, not something about subagents.

## 2. What does `claude agents --json --all` report while a subagent runs?

**`status` stays `busy` for as long as a subagent or a background shell command is running, also after the parent's turn has ended.** So "idle with children still running" doesn't occur: idle means no children.

P4, with times in UTC:

| Time | What happened | `status` | `state` |
|---|---|---|---|
| 10:33:08 | parent spawns the subagent | `busy` | `working` |
| 10:33:11 | parent's turn ends ("ZQX-PARENT-TURN-1-OVER") | `busy` | `working` |
| 10:33:11–10:34:34 | subagent runs; 25 polls | `busy` every time | `working` |
| 10:34:34 | subagent done, parent woken | `busy` | `working` |
| 10:34:38 | parent's last reply | `idle` | `done` |
| 10:34:42 | `launchBg` stops it, 102 seconds after starting it | `null` | `done` |

**Foreman's watch loop needed no change to wait.** `launchBg` returned the parent's final reply, the one written after the subagent's report, in P4, P6 and all three Q5 runs.

**A background shell command behaves the same** (P6): `busy` for the 40 seconds it ran, then the parent was woken and replied.

**`state` is not a signal.** In P6 it read `done` while the shell command was still running and `status` was `busy`, because `state` is the session's own label for its last turn. R5.3b found the same lag. Keep using `status`.

**The job record says more, if foreman ever needs it.** `state.json` has:
- `fan`: one entry per child, `{"id","kind":"agent"|"shell","label","startedAt","doneAt"}`. A child still running has no `doneAt`.
- `inFlight`: `{"tasks":1,"queued":0,"kinds":["local_agent"]}` while a subagent runs, `"kinds":["local_bash"]` for a shell command, `"tasks":0` when nothing does.

**The gap between a child finishing and the parent waking** was under 100 milliseconds in P1 (the notification at 10:30:54.981, the parent's next API request at 10:30:55.008). No poll saw `idle` in it, and `launchBg` asks for two idle looks 2 seconds apart, so the gap can't end a session by itself.

**`claude stop` does cut children off.** In P5 the session was stopped about 30 seconds into the subagent's 75-second command. The command was to write a marker file when the 75 seconds were up, and the file never appeared. So a limit that stops the parent stops its subagents too. This is the one case where the worker prompt's warning is true: work a subagent hasn't finished when foreman stops the session for a limit is lost.

## 3. Do subagents inherit `FOREMAN_ACTOR`, the guard and the deny rules?

Yes to all three, from P1.

| Check | Result in the subagent |
|---|---|
| `printenv FOREMAN_ACTOR FOREMAN_AGENT FOREMAN_BIN` (both agents) | `worker-T-0124`, `1`, `bun <main checkout>/packages/foreman/src/cli.ts` |
| Write a new `R5.3c-zqx-probe.md` in the research folder (inside the task's paths) | created |
| Write a new `zqx-probe.txt` in the packages folder (outside) | refused: "guard: packages/zqx-probe.txt is outside your task's paths (docs/research/R5.3c-*.md, docs/decisions/**); file a task for it instead" |
| Bash `echo x > packages/zqx-probe2.txt` | refused by the guard, same message |
| Bash `uname -a`, denied by `--disallowedTools` (both agents) | refused: "Permission to use Bash with command uname -a has been denied." |

So the project's PreToolUse hook runs for a subagent's calls with the session's `--settings` `env`, and the launch's `--disallowedTools` binds subagents. The guard's half of the role rules wasn't run directly, since this repo has none, but it reads the same `FOREMAN_ACTOR` that the path check used.

**An agent's own `tools:` list narrows it further.** `reviewer` is declared with `Read, Grep, Glob, Bash`. `general-purpose` listed every tool the session has, the Agent tool included. Under `dontAsk` it can still only use what `--allowedTools` permits.

## 4. Is subagent usage in the parent's transcript?

**No.** Each subagent writes its own transcript, `<session>/subagents/agent-<id>.jsonl`, with a `agent-<id>.meta.json` beside it (`agentType`, the model). The parent's transcript has no line from a subagent: zero with `isSidechain: true`. All the parent gets is one line in each notification:

```
<usage><subagent_tokens>35612</subagent_tokens><tool_uses>4</tool_uses><duration_ms>17522</duration_ms></usage>
```

`summarizeTranscript` reads only the parent's file, so foreman's limits and the cost it records miss the subagents:

| Run | Foreman counted | Subagents, uncounted | Share of cost missed |
|---|---|---|---|
| P1 (two subagents) | 4 turns, $0.0125 | 10 turns, $0.0082 | 40% |
| P4 (one) | 3 turns, $0.0043 | 2 turns, $0.0017 | 28% |
| Q5b (three) | 7 turns, $0.33 | 9 turns, $0.30 | 47% |
| Q5c (reviewer) | 7 turns, $0.24 | 4 turns, $0.06 | 19% |

The subagent files have the same shape as the parent's (assistant messages with `usage` and `model`): running `summarizeTranscript` over each one gave the figures in the third column. So the fix is to sum the parent's file and every `subagents/agent-*.jsonl` under the session's folder.

The wall-clock limit is unaffected: the parent stays `busy`, and the clock runs.

## 5. What does a fan-out cost?

One task, run three ways on `claude-sonnet-5-5`: a small library in an empty directory (an interval-set class, a parser and formatter for strings like `1-5,8,10-12`, a CLI, tests, a README), five to seven files and 380 to 540 lines.
- **Q5a, solo:** write everything, run the tests, review your own work. This is what a dispatched worker does today.
- **Q5b, fan-out:** write the code, then `test-writer`, `docs-writer` and `reviewer` in one message, then fold in their reports. This is `ship` step 3.
- **Q5c, reviewer only:** as solo, then one `reviewer`, then fold in its report.

| | Q5a solo | Q5c reviewer only | Q5b fan-out |
|---|---|---|---|
| Wall-clock, start to stopped | 75 s | 93 s (1.2×) | 83 s (1.1×) |
| Turns, parent + subagents | 3 | 7 + 4 | 7 + 9 |
| Cost, parent | $0.20 | $0.24 | $0.33 |
| Cost, subagents | none | $0.06 | $0.30 (tests $0.16, docs $0.08, review $0.06) |
| **Cost, total** | **$0.20** | **$0.30 (1.5×)** | **$0.62 (3.1×)** |
| Tests written, all passing | 65 | 31 | 65 |

**Wall-clock barely moves.** The subagents run in parallel, and each takes 20 to 40 seconds.

**The parent gets dearer, not cheaper, when it hands work off.** In Q5b the parent wrote only three of the seven files and still cost 1.6× the whole solo run: it is woken once per report, and each wake-up re-reads its context.

**What the review bought.** Q5b's reviewer found two real, minor bugs: a parse error whose message spans two lines when the bad piece holds a newline (the CLI promises one line), and `-0` kept as an interval bound, so `toArray()` returns `-0`. Q5c's reviewer found the `-0` bug too. Q5a's code has both: checked afterwards, its `parse("1-5,x\ny")` throws a two-line message and its `parse("-0").toArray()[0][0]` is `-0`. Its own review listed "negative zero" as handled and reported "Code bugs: none found".

**What the test-writer and docs-writer bought:** nothing the solo run lacked. Same test count, a comparable README. Q5b's parent also said it never read the README against the code.

**Limits of this measurement:**
- One task, one run per variant. The ratios are an indication, not a distribution.
- The task is small and new. A change inside a large codebase makes each cold agent read more, so the fan-out's cost ratio is more likely to rise than fall there. D0029 measured 10 and 32 minutes for interactive fan-out sessions against 4.3 for a dispatched solo worker.
- Sonnet 5.5, not the dispatcher's default model. Dollars scale with the price table; the ratios should carry over roughly.
- Whether a fresh verifier would have caught the two bugs wasn't tested.

## What lifting the ban would take

1. **Count subagent usage** in `launchBg` (section 4). Without it a worker with subagents can pass its turn and cost limits unseen.
2. **Rewrite the worker prompt's line.** Its reason is wrong on this version, and a worker that may spawn a subagent needs to know what section 1 found: it runs in the background, the turn ends, a notification brings the report. The worker must not submit the task before every subagent has reported.
3. Nothing in the watch loop, the guard or the launch flags.

## Cleanup

Every probe session was stopped and removed (`claude stop`, `claude rm`), and the files the probes wrote into the worktree were deleted. Nothing was committed from them.
