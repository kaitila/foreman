# D0048. Only a person, or a session a person runs, starts or stops a dispatcher (2026-11-12)

**Status:** Active

**Context:** [D0045](D0045-dispatcher-scope.md) gave a dispatcher a scope, so one plan can be run and stopped by itself. The flow people want is one interactive session that files a plan, has it executed and watches it. Until now that session ran `fm dispatch` in its own Bash: the dispatcher died with the session, taking every worker and verifier with it, and its output was a log to poll. Giving sessions a tool that starts dispatchers raises the question of which sessions may use it. Amends [D0011](D0011-foreman-dispatch.md) (who runs `fm dispatch`) and D0045 (how a plan's dispatcher is started, watched and stopped).

**Chosen:**
- **Who.** A dispatcher is started and stopped by a person, or by a session a person runs (an interactive session, its MCP server, a script of theirs). A session a dispatcher started is refused: an agent whose actor is named after a dispatched role (`worker-…`, `verifier-…`, `intake…`) gets `not_allowed` from `run_plan`, `stop_plan`, `fm plan run`, `fm plan stop`, `fm dispatch` and `fm dispatch --stop`. The check is in the core (`refuseDispatched`, `src/run-plan.ts`), so the CLI through Bash is closed as well as MCP, and `run_plan` and `stop_plan` are in every dispatched role's `--disallowedTools`. It is the same line [D0033](D0033-plans.md) draws for shaping plans.
- **`run_plan` / `fm plan run P`** starts `fm dispatch --plan P` as a detached process (its own session and process group, stdin closed, output appended to `.foreman/dispatch-<plan>.log`), waits until it shows in the registry ([D0041](D0041-dispatcher-registry.md)), and returns its pid, scope and log. It acts as the caller, so the registry names who started it. It marks nothing ready. When a dispatcher that starts workers already covers the plan (the plan's own, or the whole-board one), that one is returned with `started: false` and nothing is started. A dispatcher that ends at once because nothing of the plan can start is an error (`nothing_to_run`), not a start.
- **`watch_plan` / `fm plan watch P`** is how a session follows it. Without `since` it returns the state at once. With `since` (an event id) it returns when an event after it is one the watcher should act on (a task of the plan submitted, passed, failed, waiting for approval, its session gone without a result, approved, merged, cancelled), when no dispatcher covers the plan, when the plan is done or cancelled, or after a timeout (60 s by default, 10 min at most). It returns what happened, each task's status with the short form of what it waits on, live sessions with their last lines, the tasks waiting for a person, and `next`, the event id to pass next time. It reads the events table and the registry; nothing new is stored.
- **`stop_plan` / `fm plan stop P`** is `fm dispatch --stop P`: the dispatcher started for that plan.
- **The `run-plan` skill** (agent-kit) is the session's side: shape the plan, show it, mark the tasks ready on the person's yes, `run_plan`, loop on `watch_plan`, and report what is left for the person to sign off. The session never does a task of a plan a dispatcher covers, never verifies and never approves.
- **A second try is a second run.** A failed verdict already puts the task back to `ready` with the verifier's evidence for its next worker (`recordVerify`, T-0064), and the dispatcher gives each task one worker per run. So the skill gives a failed task its one retry by calling `run_plan` again once the dispatcher has ended. It doesn't call `rework_task`: that is for a task in review, by someone who worked on it or a person, and the watching session is neither.

**Why:**
- A dispatcher turns ready tasks into sessions that cost money, each within its own budget. A person decides to spend that, directly or through the session they are talking to, which shows them the plan first. A worker that could start a dispatcher could start work nobody agreed to, on any plan, from inside a session nobody watches; a worker that could stop one could throw away its siblings' unpushed work. Neither has a reason to: a worker that finds more work files a task.
- The limit is a guardrail of the same kind as D0033's, and as strong: the actor's name comes from the environment the dispatcher sets. The hard limits stay outside the agent (D0003): each session's budget and turn limit, and `--max`.
- Detached, because the dispatcher has to outlive the session that asked for it: a plan's later steps start after earlier ones merge, which can be hours later, and stopping a dispatcher stops its sessions. A session that ends, a closed terminal or a restarted MCP server must not do that by accident. Stopping it is a deliberate call, by plan id.
- A log is for reading afterwards. A watcher needs "what changed since I last looked", and the events table already numbers every change, so an event id is a cursor that costs nothing and can't miss or repeat an event. Returning only on events worth acting on keeps a watching session's context small: one call per outcome, not one per poll.
- Returning the dispatcher that already runs, where `fm dispatch` refuses, lets a session that was restarted pick up the plan it was watching with the same call.

**Revisit if:** dispatchers run on another machine than the session (a pid and a local log no longer do), a watcher needs events of more than one plan in one call, sessions start dispatchers without showing the plan to the person first (then the yes has to be recorded in foreman, not left to the skill), or a retry inside one run is wanted (then the dispatcher's one try per task changes, not the skill).
