# D0045. A dispatcher has a scope: the whole board or named plans (2026-11-12)

**Status:** Active

**Context:** [D0011](D0011-foreman-dispatch.md)'s dispatcher took every ready task on the board. The only way to keep a task from it was to leave it a draft, so a person couldn't say "run this plan and nothing else", and a session couldn't start the work of one plan and watch it to the end. [D0041](D0041-dispatcher-registry.md) gave a running dispatcher a record with a `scope` that was always `everything`, and [D0042](D0042-plan-steps-gate.md) made a plan's steps hold. Amends D0011 (what a dispatcher takes, and when it ends), D0041 (the scope has values, and one record per scope) and D0042 (one more reason and one more leaf).

**Chosen:**
- **Scope.** `fm dispatch --plan P-0004` (repeatable) starts workers only for ready tasks in those plans and verifiers only for their `in_review` tasks. Without `--plan` the scope is `everything`, as before. The registry's `scope` is `everything` or the plan ids, sorted and joined with commas (`P-0004,P-0007`). A plan that doesn't exist or is cancelled is refused. Everything else is unchanged: `--max`, one try per task and run, and the rule for what can start (`waitsOn`), so a plan's tasks start in step order.
- **A plan dispatcher stays up** while its plans hold something it would still start: a submitted task waiting for a verifier, a task another session holds, or a ready task whose path ends in a running session or in a task that something will pick up. It ends by itself when everything of its plans is done, approved, waiting for a person (a draft, risk human, an approval, a stuck blocker) or has had its one try in this run. `--once` ends as before. The whole-board dispatcher still ends as soon as nothing runs.
- **One dispatcher per scope.** A second one with the same scope is refused, with the first one's pid in the message; the check and the record are written in one transaction. Different scopes run side by side, a plan's dispatcher beside the whole-board one included. They can't start the same task (a claim is atomic), and each counts path overlaps against every task in flight, the other's too, because the rule reads the board, not the dispatcher's own list.
- **Stop.** `fm dispatch --stop <pid|plan>` finds the dispatcher in the registry (by pid, by a plan its scope names, or `everything`), sends it SIGTERM, which it handles as it does Ctrl-C (its sessions stopped, its record removed), waits for it and its sessions to be gone, and releases their leases there and then: a worker's task is `ready`, a verifier's `in_review`. Only a pid in the registry is ever signalled. A plan that two dispatchers cover needs the pid.
- **A new reason, `no dispatcher`.** A ready task with nothing else to wait on that no running dispatcher would start: none runs, or none whose scope covers it. A `--verify-only` or `--once` dispatcher doesn't count, since it starts no new workers. It is also a leaf kind of the path, so a chain can end in "can start, but no dispatcher covers it". It holds nothing: `claim` and `next_tasks` ignore it, and a dispatcher ignores it when deciding what to start. It shows in `fm show`, `fm list`, `list_tasks` and `next_tasks`. The board reads the rule with it too (since T-0120): such a task reads "can start: no dispatcher covers it", and its plan's header names the dispatchers that cover the plan or gives the command to start one ([the board's design](../board-design.md)).

**Why:**
- A plan is the unit a person decides to run. Leaving every other task a draft to get that is a workaround that also hides those tasks from sessions working by hand.
- A plan's later steps can only start after earlier ones merge, which a person or the merge queue does. A dispatcher that ended whenever nothing ran would end after step 1 every time, so it has to wait; but it must not wait on something only a person can move, or it would never end.
- Two dispatchers with the same scope would only race each other for the same tasks and double the sessions a person expects from `--max`. Refusing the second, with the pid, also tells a session that the plan it wants to start is already running.
- Stopping by plan is what the person knows; the pid is what the registry needs. Releasing the leases in `--stop` means the tasks are free when the command returns, not at the next reclaim.
- Before scopes, "ready with nothing to wait on" meant "the dispatcher will start it". With scopes it can also mean "nobody will", and that looks the same as "can start" unless it is said.

**Revisit if:** a scope other than plans is wanted (a label, a path, a single task), two dispatchers for one plan are wanted on purpose (more slots: raise `--max` instead), a plan dispatcher that waits on a task held by hand for days is a nuisance (then a limit on waiting), or dispatchers run on more than one machine, where a pid can't be signalled.
